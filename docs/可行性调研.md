# Shader Forge 图到程序逻辑 Shader：可行性调研

调研日期：2026-09-20。依据 [Shader Forge 官方仓库](https://github.com/FreyaHolmer/ShaderForge) 的 `master` 提交 `3bde185e67178b687b4d0b1964367355aef471f8` 及 Unity 文档。这里的“保留实现”指在指定 Unity 版本、渲染管线和测试场景下保持材质属性、渲染状态及可观察画面；不能仅凭源码相似或编译通过认定等价。当前探针已完成 Unity 导入/编译检查，尚未完成画面对比。

## 1. 目标重新定义

输入是 Shader Forge 产生的 `.shader`（其中通常同时包含 `SF_DATA` 节点图和 ShaderLab/CGPROGRAM）。输出应是一份**按程序逻辑编排的 Shader**：

- 材质参数有清晰用途；节点链变成可理解的计算步骤，例如 UV 动画、遮罩、法线、光照、最终颜色。
- 在顶点和片元阶段分别表达计算；可以安全复用的计算抽成函数，重复变量和无意义的 `node_123` 名称得到整理。
- 保留原来的 ShaderLab 属性、渲染队列、Blend/ZWrite/Cull、Pass、光照、阴影、关键词和必要的 Unity 宏，除非某项变更通过了单独验证。
- 输出能脱离 Shader Forge 编辑器编译，并附带转换说明：每个主要逻辑块来自哪些节点、哪些部分仍是原生成代码、哪些行为尚未验证。

**只删除 `SF_DATA`、换名称、调缩进不满足目标。** 这些仅是导出准备步骤，不计作逻辑化转换成果。

## 2. 为什么有条件可行

Shader Forge 在 `.shader` 文件头保存 `/*SF_DATA;...*/`：其中有节点类型、ID、连线、属性、节点备注、输出端口和部分设置；后面接完整的 ShaderLab 源码。生成器将两段一起写盘。[序列化代码](https://github.com/FreyaHolmer/ShaderForge/blob/master/Shader%20Forge/Assets/ShaderForge/Editor/Code/SF_EditorNodeView.cs#L728-L754)、[保存代码](https://github.com/FreyaHolmer/ShaderForge/blob/master/Shader%20Forge/Assets/ShaderForge/Editor/Code/_Evaluator/SF_Evaluator.cs#L3315-L3339)、[示例 Shader](https://github.com/FreyaHolmer/ShaderForge/blob/master/Shader%20Forge/Assets/ShaderForge/Example%20Assets/Shaders/VertexAnimation.shader)

这给转换器两个互补的信息源：

| 信息源 | 能提供什么 | 单独使用的缺陷 |
| --- | --- | --- |
| `SF_DATA` 节点图 | 计算依赖、节点类型、最终输出端口、属性名称、用户备注 | 不直接给出 Unity 光照、Pass 和平台宏的全部最终代码；老版本格式及自定义节点可能有差异 |
| 已生成的 `.shader` 正文 | 实际运行的 ShaderLab、顶点/片元函数、Pass、宏和渲染状态 | `node_编号` 与大段生成样板丢失了节点意图；直接全文改写很难保证等价 |

因此推荐**图与生成代码联合分析**：图帮助恢复“算什么”，原代码确定“怎么算、在哪个 Pass 中算”。上游解析器本身按 `n:`、`ps:` 等记录恢复图；其代码也标出转义分隔符、SubShader 支持方面的 TODO，说明不能假定所有历史数据都是无歧义、完整的格式。[SF_Parser.cs](https://github.com/FreyaHolmer/ShaderForge/blob/master/Shader%20Forge/Assets/ShaderForge/Editor/Code/SF_Parser.cs#L47-L115)

### 真实例子：顶点动画示例

上游 `VertexAnimation.shader` 的图里有 Panner、Frac、Subtract、Abs、Multiply、Power 节点，Power 节点标了 “Panning gradient”；该结果同时参与顶点偏移、漫反射混合和自发光。生成代码中，这条链在 `vert` 和 `frag` 各出现一次，并以 `node_133`、`node_1924` 等名称暴露。[节点图及生成代码](https://github.com/FreyaHolmer/ShaderForge/blob/master/Shader%20Forge/Assets/ShaderForge/Example%20Assets/Shaders/VertexAnimation.shader)

理想输出应显式表达为“由滚动 UV 形成周期渐变 → 用渐变偏移顶点 → 用同一渐变调制颜色/发光”。对**相同阶段内部**可考虑共用一个命名函数；顶点和片元各自执行的计算不能仅因表达式相同就随意合并成一个运行结果，因为插值位置及精度会改变效果。下面只是目标结构示意，**不是该示例的已验证转换结果**：

```hlsl
float ComputePanningGradient(float2 uv, float timeY, float shape)
{
    float phase = frac(uv.x + timeY * 0.25);
    float triangle = abs(phase - 0.5) * 2.0;
    return pow(triangle, shape);
}

// vertex: gradient -> vertex offset
// fragment: gradient -> diffuse / emission
```

## 3. 技术路线比较

| 路线 | 实现方式 | 对目标的贡献 | 判断 |
| --- | --- | --- | --- |
| 只清理现成文本 | 删除元数据、格式化、简单重命名 | 很难恢复计算意图，效果有限 | 只能作导出底座 |
| 只从图重新生成全部 Shader | 自建节点编译器及光照/Pass 生成器 | 输出控制强 | 工作量和等价风险很高，不适合首版 |
| **图 + 原代码混合重构** | 图建依赖模型；源码建 Pass/函数/语句模型；只重构能映射并验证的片段 | 可逐类把节点链变成程序逻辑，同时保留原实现的安全底座 | **推荐** |
| 修改 Shader Forge 生成器 | fork `SF_Evaluator` 改输出 | 生成时可拿到内部节点语义 | 与上游内部状态耦合，旧 Shader 仍需重生成；可作为后续研究 |

混合路线应采用**渐进式转换**：未覆盖的节点或 Pass 原样保留在清晰标出的 `Generated fallback` 区域，报告覆盖率。不能把“有 fallback”报告为“已完成手写化”。

## 4. 可重构与不可贸然重构的部分

**首批适合尝试：** Unlit 或简单效果中的常量、属性、基础算术、UV 变换、纹理采样、颜色混合、遮罩、裁剪、顶点偏移。它们通常能从节点依赖恢复计算步骤，并在生成源码中找到对应语句。命名优先取材质属性名、节点备注、最终输出用途；自动命名不明确时可使用保守的 `mask_1` 等名称并允许人工改名。

**高风险：** PBR/GI、ForwardAdd/Deferred/ShadowCaster/Meta 等多 Pass、关键字分支、实例化、曲面细分、GrabPass/折射、自定义光照或自定义节点。生成器里确实有跨 Pass 代码、`GrabPass` 和自定义 Inspector；不能把这些当“冗余模板”删除。[SF_Evaluator.cs](https://github.com/FreyaHolmer/ShaderForge/blob/master/Shader%20Forge/Assets/ShaderForge/Editor/Code/_Evaluator/SF_Evaluator.cs#L3029-L3042)、[多 Pass 示例](https://github.com/FreyaHolmer/ShaderForge/blob/master/Shader%20Forge/Assets/ShaderForge/Example%20Assets/Shaders/TessellationDisplacement.shader)

**保持现状也会影响独立性：** 生成结果末尾可能有 `CustomEditor "ShaderForgeMaterialInspector"`；保存流程还给 ShaderImporter 设置默认纹理。转换器必须处理或报告这些依赖；不能只对文本做替换就声称材质效果完全保留。[自定义 Inspector](https://github.com/FreyaHolmer/ShaderForge/blob/master/Shader%20Forge/Assets/ShaderForge/Editor/Code/_Evaluator/SF_Evaluator.cs#L3029-L3031)、[默认纹理](https://github.com/FreyaHolmer/ShaderForge/blob/master/Shader%20Forge/Assets/ShaderForge/Editor/Code/_Evaluator/SF_Evaluator.cs#L3342-L3390)

## 5. 推荐的转换模型

1. **解析输入。** 严格界定 `SF_DATA`；读取节点、端口、边、属性、备注及最终输出。对未知记录保留原文并报不支持，不静默丢弃。
2. **解析生成代码。** 至少识别 ShaderLab 顶层结构、每个 Pass、CGPROGRAM/HLSLPROGRAM、预处理分支、顶点/片元入口、声明及语句。字符串与注释必须被词法层正确处理；不能对全文做正则替换。
3. **建立映射。** 用 `node_编号`、属性名、输出通道、生成器命名规律寻找图节点与代码片段的对应；每个映射带置信/证据。匹配不到就保留源码。
4. **构建阶段内数据流。** 对可确认的表达式做依赖排序、命名、分组；区分顶点、片元、各 Pass，不跨阶段随意移动运算。
5. **生成结构化源码。** 分出参数、UV/采样、效果核心、光照/输出等区域；只有能保持输入、输出、宏上下文和求值位置的连续逻辑块才抽函数。
6. **验证并报告。** 比较编译、属性/Pass/状态契约、材质默认值与截图；每条转换规则可单独禁用并回退到原生成片段。

这属于**受限源码重构器**，需要中间表示和代码生成器。简单的格式化器或一组全局正则不足以兑现目标。现有 [Shader Graph Cleanup 工具](https://github.com/Agentlien/ShaderCleanup)说明“整理生成代码”有先例，但它处理的是 Shader Graph，规则不能直接迁移到 Shader Forge。

## 6. 验证与可行性门槛

建议先做一个只覆盖 **Unlit + 基础算术/UV/纹理/混合** 的技术探针。通过门槛：

- 一个真实节点图能自动输出至少一段有意义的命名计算，并给出节点 ID → 输出函数/变量的映射；不是只改 `node_123` 的名字。
- 输出文件能在目标 Unity 工程编译；材质属性、纹理默认值、渲染状态和所需 Pass 没有非预期改变。
- 固定场景中输出与原 Shader 做图像对照；记录差异和测试条件。编译通过本身不等于效果等价。
- 遇到不支持的节点、Pass 或歧义时明确标 `Partial`/`Unsupported`，保留原代码，不伪造“成功转换”。

若探针无法可靠建立图与代码的映射，路线应调整为“半自动重构助手”：生成逻辑分组和节点注释供开发者确认，而非自动宣称完成转换。

## 7. 范围与授权

首轮目标为 **Unity 2022.3 LTS + Built-in Render Pipeline**，这是建议的测试基线，不是已证实的支持范围。把 Built-in Shader 改写为 URP/HDRP 是另一类迁移问题；Unity 的管线功能并不完全对应。[Unity 功能比较](https://docs.unity3d.com/6000.0/Documentation/Manual/render-pipelines-feature-comparison.html)
